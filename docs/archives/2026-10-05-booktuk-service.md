# 책툭 구상 기록 (폐기)

상태: **폐기된 구상** (2026-10-05). 북썸의 현재 개발 후보나 구현 지침으로 사용하지 않는다. 대화 중 검토한 서비스 정의와 기술·품질 위험을 기록으로 남긴다.

폐기 이유: 질문의 사실·정답·독자가 읽은 위치·재미를 모두 안정적으로 보장하기 어렵다. 작은 오류나 스포일러가 독서 경험의 신뢰를 크게 해칠 수 있고, 사람 검수에 의존하면 책의 수에 맞춰 확장하기 어렵다. 북썸의 매력은 다른 방향에서 다시 구상한다.

## 한 문장 정의

**책툭**은 독자가 *이미 읽은* 책 속의 구체적인 사실을 짧고 가볍게 묻는 북썸의 독서 게임이다. 질문은 읽는 중이나 독서가 뜸해졌을 때 뜻밖에 도착할 수 있다. 좋은 문제가 없으면 아무것도 보내지 않는다.

책툭은 북썸의 여러 서비스 중 하나다. 독서 기록, 내 서재, 공개 책 이야기의 대체물이 아니며, 모든 책이나 모든 독자에게 질문을 제공한다는 약속도 하지 않는다.

## 대화에서 정한 핵심 방향

1. 독자가 등록한 책의 `currentPage / totalPages`로 대략적인 독서 위치를 계산한다. 판본의 흐름이 대체로 비슷하다는 점을 활용하되, 이 비율이 정확한 장면 위치라는 뜻은 아니다.
2. AI가 알고 있는 작품의 흐름과 이용 가능한 근거를 바탕으로 **읽은 범위 안의** 문제를 만든다. 셀 수 없이 많은 책을 미리 처리하지 않고, 북썸에서 실제로 읽히는 책에 대해서만 필요할 때 생성한다.
3. “A는 남자인가요?”, “그날 먹은 음식은?”처럼 인물·행동·사물·장면을 묻는 **짧고 구체적이며 가능하면 위트 있는 단답형**이 중심이다. 반드시 정답 하나가 있어야 한다. 정답이 확인되지 않는 사소한 디테일은 꾸며내지 않는다.
4. 질문의 **도착 시점**은 일정 범위에서 무작위일 수 있다. 독서 중에는 작은 놀이가 되고, 뜸해졌을 때는 부담 없는 상기가 된다. 무작위성은 출제 시점에 적용하며, 읽지 않은 내용까지 임의로 고르는 근거가 되지 않는다.
5. AI가 작품을 잘 모르거나, 질문의 사실·정답·등장 위치·재미가 불확실하면 **출제하지 않는다**. 발송률보다 신뢰가 우선이다.
6. 책툭은 독자를 시험하거나 독서량을 재촉하지 않는다. 문제를 건너뛰거나 “기억 안 나요”를 고를 수 있다.

## 사용자 경험

1. 독자가 내 서재에 책을 등록한다. 현재 북썸에서는 전체 페이지 입력이 선택 사항이며, 책툭의 페이지 기반 출제를 위해서는 전체 페이지가 필요하다. 값이 없거나 현재 페이지가 0이면 책툭은 기다린다.
2. 독자가 읽은 페이지를 갱신하면 서버가 해당 책의 진도를 계산한다. 예: 300쪽 중 90쪽이면 약 30%. 이때 30% 지점에 있는 일을 묻지 않고, 충분히 앞선 구간에서 확인된 사실을 고른다.
3. 출제 가능한 문제가 있으면 읽는 화면이나 서재에서 짧은 카드로 보여줄 수 있다. 모바일 푸시에 동의한 독자에게는 허용된 시간대에 알림을 보낼 수 있다. 푸시가 없거나 거부된 독자도 앱 안에서 참여할 수 있어야 한다.
4. 문제를 열면 한 줄 질문과 간단한 답변 입력 또는 2~3개 선택지를 보여준다. 선택지의 오답도 읽지 않은 내용을 암시해서는 안 된다. “모르겠어요”, “나중에”도 제공한다.
5. 답변 뒤 정답과 짧은 설명을 보여준다. 가능한 경우 어느 장면에 근거한 문제인지 **스포일러 없이** 알려준다. 독자는 “틀린 내용”, “아직 안 읽은 내용”, “재미없음”을 신고할 수 있다.
6. 같은 문제를 같은 독자에게 반복하지 않는다. 독자가 책을 완독하거나 책툭을 끄면 해당 책의 대기 중인 알림을 취소한다.

알림 문구는 잠금 화면에 줄거리·정답·미래 인물 이름을 노출하지 않는 것이 기본이다. 예: “《칼의 노래》에서 책툭이 왔어요.” 실제 질문은 앱을 연 뒤 보여준다.

## 질문의 품질 기준

| 통과 조건 | 탈락 예시 |
| --- | --- |
| 해당 작품 안에서 확인 가능한 사실이다. | 일반 역사 상식만 묻거나, 책에 없는 식사를 상상한다. |
| 정답을 한 단어·짧은 구절 또는 명확한 보기 하나로 답할 수 있다. | “주인공의 삶에서 가장 중요한 것은?”처럼 해석마다 답이 달라진다. |
| 독자가 읽은 범위보다 충분히 앞에서 이미 나온 사실이다. | 등장 위치를 모르거나, 질문·보기·해설이 뒷부분을 누설한다. |
| 책을 읽은 사람에게 작고 즐거운 기억 환기가 된다. | 제목·저자만 보고도 누구나 맞히는 상식 문제, 시험 문제 같은 암기 문항. |
| 질문·정답·해설이 같은 근거와 일치한다. | 생성 모델과 검토 모델이 서로 동의하지만 근거는 제시하지 못한다. |

‘이순신은 왜 고독했을까요?’는 너무 넓다. ‘이순신이 그날 저녁 먹은 음식은?’은 책에 실제 음식과 장면이 확인될 때만 좋다. 앞서 예로 든 ‘백의종군은 네 글자로?’처럼 사실이어도 너무 뻔하면 품질 검사에서 탈락할 수 있다.

### 환각과 스포일러를 줄이는 출제 게이트

후보 하나마다 `질문`, `정답`, `허용 답안`, `간단한 설명`, `작품 식별자`, `근거 출처/위치`, `최초 출제 가능 진도`, `품질 판정`을 만든다. 근거 출처는 이용 가능한 도서 소개·목차·정식 미리보기·검토된 문항·독자가 사용을 허용한 자신의 기록 등이 될 수 있다. **AI의 기억과 자체 확신 점수는 후보 생성에 활용할 수 있지만, 그것만으로 정확성 검증이 끝나지는 않는다.** 확인 가능한 근거가 없으면 알림 발송 대상으로 승인하지 않는다.

게이트는 순서대로 적용한다.

1. **도서 식별:** 제목만으로 합치지 않는다. ISBN과 저자·판본을 확인하고, 어린이용 축약본·각색본·번역 차이가 큰 판본은 별도로 취급한다.
2. **사실 검증:** 정답이 근거에서 직접 확인되는지, 질문이 사실 이상의 동기·감정·인과관계를 지어내지 않았는지 확인한다. 가능하면 문제 생성과 별개 절차가 같은 근거를 대조한다. AI 두 번의 동의는 독립적인 증거가 아니다.
3. **위치 검증:** 사실이 책의 어느 부분에서 처음 드러나는지 추정하거나 확인한다. ‘독자 진도 30%’라는 이유로 경계인 30%의 사건을 출제하지 않는다. 초기 가안은 최소 10%포인트의 여유를 두고 20% 이전에서 고르는 것이다. 이 수치는 파일럿에서 조정한다. 등장 순서가 불확실한 문제는 보류한다.
4. **형식·재미 검증:** 정답의 유일성, 짧은 응답, 문장의 자연스러움, 뻔한 상식 문제 여부를 검사한다. 품질 점수만 높고 근거가 없는 문제는 탈락한다.
5. **발송 직전 재검사:** 독자의 최신 페이지·도서 상태·알림 설정·기존 출제 이력과 문제 승인 상태를 다시 확인한다. 그사이 책이 바뀌거나 문제가 신고되어 중단됐다면 보내지 않는다.

**실패 결과는 `문제 없음`이다.** 오류나 근거 부족을 억지 질문으로 메우지 않는다. 같은 질문을 만든 뒤 다른 모델에게 “확실한가?”만 묻는 방식은 검증으로 취급하지 않는다.

## 생성·선정·발송 프로세스

```text
책 등록/진도 갱신
  → 독자·책의 출제 적격성 확인
  → ISBN/작품별 승인된 질문 조회
  → 부족할 때만 질문 후보 생성
  → 근거·위치·재미 게이트 통과분 저장
  → 독자 진도에 맞는 미출제 질문 선택
  → 무작위성이 있는 발송 시점 예약
  → 발송 직전 재검사
  → 앱 카드 또는 동의한 모바일 푸시
  → 답변/건너뛰기/신고 → 문제 품질 개선
```

- **지연 생성과 재사용:** 전체 도서에 대해 선제 생성하지 않는다. 실제 독자가 읽는 책의 해당 구간에 승인 문제가 없을 때 소수의 후보만 만든다. 동일한 작품·판본의 검토된 문제는 재사용하되, 특정 독자의 비공개 기록에서 만든 문제는 다른 독자에게 공유하지 않는다.
- **무작위 발송의 경계:** 선택 가능한 문제 중에서만 시점을 흔든다. 발송 빈도 상한, 최소 간격, 조용한 시간, 책별 끄기, 전체 끄기를 둔다. 독서가 뜸할 때도 반복 독촉하지 않는다. 구체적인 일수·빈도는 사용자 시험에서 정한다.
- **읽는 중의 의미:** 현재 앱에는 독서 세션 감지가 없다. 첫 버전은 서재/독서 화면 진입이나 진도 저장 직후의 앱 내 카드로 시작할 수 있다. 실제 독서 중임을 더 정확히 감지하는 기능은 후속 범위다.
- **오류와 비용:** 생성 실패·외부 자료 부재·AI 장애는 독자의 책 등록/기록을 막지 않는다. 같은 책·구간에 대한 중복 생성 요청을 합치고, 호출 횟수·비용·재시도를 제한한다.

### AI 호출 계약 초안

생성기는 `책 식별자(ISBN·제목·저자·판본)`, `독자 진도`, `출제 가능한 최대 서사 위치`, `이용 가능한 근거`를 입력받는다. 응답은 후보 목록 또는 `no_question` 중 하나다. 후보에는 질문·정답·허용 답안·짧은 해설·근거 위치·최초 출제 가능 위치를 구조화해 담는다. **후보 0개가 정상 응답**이어야 한다. 모델이 근거를 만들거나 위치를 확정할 수 없으면 `no_question`을 반환하도록 지시한다.

서버 검증기는 모델 출력의 형식만 확인하고 통과시키지 않는다. 근거 참조의 유효성, 답과 근거의 일치, 위치의 안전 여유, 중복 문항, 보기에 들어간 스포일러까지 확인한다. 모델 버전·프롬프트 버전·근거 버전을 저장해 문제가 신고됐을 때 같은 방식으로 재현할 수 있게 한다.

## 현재 코드와 구현 경계

2026-10-05 현재 확인한 상태다. 코드가 바뀌면 구현 전에 다시 점검한다.

| 항목 | 현재 상태 | 책툭에서 할 일 |
| --- | --- | --- |
| 독서 위치 | `reading_books`에 ISBN, `current_page`, 선택적인 `total_pages`, `progress_percent`, 상태가 있다. Expo의 `src/components/reading-progress.tsx`에서 갱신한다. | 서버에서 유효한 위치를 다시 계산하고, 진도 변경을 책툭 후보 선택의 계기로 쓴다. |
| 작품·판본 | `book_works`, `book_editions` 테이블이 있지만 개인 `reading_books`에는 이 테이블로 향하는 FK가 없다. | 우선 ISBN 단위로 안전하게 식별하고, 작품 간 질문 재사용에는 별도의 작품/판본 매핑을 마련한다. |
| 알림 | `push_tokens`, `notifications` 테이블은 있으나 현재 앱·서버에 책툭 푸시 등록/발송 흐름이 없다. 루트 `package.json`에도 `expo-notifications`가 없다. | 앱 내 카드부터 구현하고, 푸시는 토큰 등록·권한·스케줄·수신 화면 이동·실패 처리까지 별도로 만든다. |
| AI | 책툭 생성기, 질문 저장소, 검토 파이프라인, AI 제공자 설정이 없다. | 서버에서만 AI 호출과 비밀키를 관리한다. 클라이언트와 공개 웹에 비밀키를 넣지 않는다. |
| 인증 경계 | Expo 네이티브 앱과 `/app/` 웹 빌드가 Spring API를 사용한다. `/app/` 웹은 같은 출처의 `/api/reader/**`와 HTTP-only 쿠키 경계를 따른다. | 책툭 읽기/답변 API도 동일한 인증 경로를 사용한다. 브라우저나 모바일이 DB에 직접 접근하지 않는다. |

새 기능은 `server/`의 Spring API와 새 Flyway 마이그레이션으로 구현한다. 기존 `V1__create_booksome_schema.sql`을 고치지 않는다. 예시 데이터 모델은 다음과 같으며 이름과 세부 컬럼은 구현 시 확정한다.

- `booktuk_questions`: 책/판본 식별자, 질문·정답·선택지, 근거 종류와 위치, 최초 출제 가능 진도, 승인 상태, 모델/검토 버전, 생성 시각. 문제 내용과 근거는 관리자 검토·중단이 가능해야 한다.
- `booktuk_deliveries`: 사용자·서재 책·문항, 예약/발송/열람/답변/건너뛰기 상태, 시간, 중복 방지 키. 독자의 답은 기본적으로 비공개다.
- `booktuk_preferences` 또는 기존 설정의 확장: 책별/전체 켜기, 모바일 푸시 동의, 조용한 시간 등. OS 푸시 권한과 서비스 내 선호를 구분한다.
- `booktuk_reports`: 사실 오류, 스포일러, 재미없음 등의 신고와 조치 이력. 신고된 문항은 재검토 전까지 발송을 멈출 수 있어야 한다.

질문 생성 요청에는 필요한 도서 식별 정보와 진도만 보낸다. 독자의 비공개 문구·사진을 AI나 공용 질문 저장소에 넣는 기능은 기본 범위에 포함하지 않는다. 향후 독자 개인 기록을 활용한다면 별도 선택과 공개/보관 범위를 설계한다. 도서 전문을 외부 AI에 제공하는 방식은 자료 사용 권한과 보관 정책을 검토한 뒤 결정한다.

## 단계별 구현 순서

1. **질문 파일럿:** 장르와 인지도에 차이가 있는 실제 책 소수로 AI 후보를 생성한다. 사람이 사실·정답·대략적 등장 위치·재미·스포일러를 검토한다. 질문이 0개인 책도 정상 결과로 기록한다.
2. **앱 내 첫 경험:** 유효한 진도와 승인 문제를 연결해 앱 안에서만 보여준다. 답하기, 모르겠어요, 건너뛰기, 신고, 재출제 방지를 구현한다. 빈 상태에서는 책툭을 억지로 노출하지 않는다.
3. **서버 자동화:** 책이 실제로 읽힐 때만 생성하고, 후보·검증·승인·보류 이력을 저장한다. 자동 승인 범위는 파일럿의 오류 유형을 본 뒤 정한다. 관리자 콘솔에서 문제를 찾아 비활성화할 수 있게 한다.
4. **알림 실험:** 앱 내 경험의 품질이 확인된 후 모바일 푸시를 추가한다. 조용한 시간·빈도·독서 중/휴면 상황별 반응을 확인한다. 웹에서는 푸시를 필수 전제로 삼지 않는다.

## 검증과 성공 판단

- **정확성:** 표본 문제의 정답과 근거가 일치하는지, 소설 속 사실과 일반 배경지식을 혼동하지 않는지 사람이 확인한다. 사실 오류·스포일러 신고를 책/문항/모델 버전별로 집계한다.
- **진도:** 여러 판본과 전체 페이지 미입력·변경, 페이지 역행, 완독, 책 삭제를 시험한다. 경계 진도와 발송 직전 진도 변경에서 미래 내용이 노출되지 않아야 한다.
- **참여:** 보낸 수보다 열어본 비율, 답변/건너뛰기 비율, “기억 안 나요”와 신고 이유, 알림 끄기 비율을 본다. 다시 책을 펼쳤는지는 별도 사용자 조사로 확인한다. 알림 클릭만으로 독서 복귀를 단정하지 않는다.
- **중단:** 문제를 운영 중 비활성화하면 대기 중 발송도 취소되는지 확인한다. AI 장애 시 독서 기록 흐름이 정상인지 확인한다.

첫 출시의 목표는 발송량이 아니다. **독자가 “책을 제대로 읽고 내게 묻는구나”라고 느끼는 소수의 문제**를 만들고, 틀리거나 앞질러 간 질문은 빠르게 멈추는 것이다.

## 당시 남아 있던 미결정 항목

- AI 제공자·모델, 호출 비용 상한, 이용 가능한 도서 근거의 범위와 사용 권한.
- 자동 승인 가능한 근거의 종류와 사람 검토가 필요한 책/문제의 범위.
- 진도 안전 여유, 문항 길이·답변 형식, 하루·주간 알림 상한과 휴면 판정 기간.
- 앱 내 기본 제공 여부와 모바일 푸시의 명시적 선택 방식.
- 책툭 참여 이력을 내 서재에서 어떻게 보여줄지와 보관 기간.
